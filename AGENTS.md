# Правила проекта

> Карта архитектуры: `docs/ARCHITECTURE.md`. База знаний по фичам: `docs/INDEX.md` (каждая фича — свой док в `docs/features/`, связанных ссылками). Правила тестирования: `docs/TESTING.md`.

## Стек

Bun + Vite (React 19, React Router) + Hono + Drizzle ORM + PostgreSQL — без Next.js, без Prisma. Один Hono-процесс на :3000 отдаёт собранный SPA, REST API (`/api`) и MCP-сервер (`/api/mcp`).

- REST-роуты — `server/routes/**`, MCP-сервер — `server/mcp.ts`, страницы — `src/pages/**`, UI-компоненты — `src/components/**`, общая логика — `src/lib/**`.
- Схема БД — `src/db/schema.ts` (клиент реэкспортится из `@/db`), миграции — `drizzle/` (`bun run db:generate` / `db:migrate`).
- `bun run dev` поднимает Vite (UI на http://localhost:5173, проксирует `/api`) и API на :3000.

## Правила

1. После завершения работы обязательно запускай `bun run typecheck` — это главный гейт. `bun run lint` должен оставаться чистым: исправляй и warnings, не только errors.
2. После всех изменений форматируй изменённые файлы: `bunx prettier --write <files>` (конфиг — `.prettierrc`). Весь репозиторий целиком не переформатируй — кодовая база написана без форматтера, полный прогон даст огромный бессмысленный диф.
3. Не пиши всё в одном файле. Один файл — один компонент (или одна функция/модуль логики). Если требуется больше — создавай папку, объявляй в ней все связанные компоненты, а вспомогательные функции выноси в `helpers.ts`.
4. Мы пишем типобезопасный код. Не ослабляй типы через `any` и `as` без необходимости; делай пропсы и поля обязательными там, где это логически обосновано, чтобы избежать лишних проверок на null.
5. Оператор `!` (non-null assertion) допустим только в исключительных случаях. Старайся использовать `?.`, явные проверки или сужение типов.
6. Следи за клиент/серверной границей. `src/lib/stores/**`, `src/lib/appService.ts`, `cheerio`, `google-play-scraper` и прямой доступ к БД — серверное. Не импортируй серверные модули из клиентских компонентов: они утянут server-only зависимости в браузерный бандл. Общие чистые хелперы выноси в отдельные файлы — эталон паттерна: `src/lib/metricColor.ts` и `src/lib/storeLinks.ts` живут отдельно от `research.ts` именно поэтому.
7. Не выполняй тяжёлые вычисления прямо в рендере React-компонента — `useMemo` или вынос из компонента. Старайся писать оптимизированный код.
8. Перед работой над фичей открой её док в `docs/features/` (см. `docs/INDEX.md`). Если дока нет — создай по шаблону `docs/features/_TEMPLATE.md`. После любой правки фичи **обновляй** её док: держи его тощим (ссылки на код, а не копия), синхронным с кодом, со связями на родственные фичи. Протухший док хуже отсутствующего.
9. Тесты пиши по правилам из `docs/TESTING.md`: раннер — `bun test`, файлы `*.test.ts` рядом с кодом. Новая чистая логика в `src/lib/**` покрывается тестом. После написания запускай `bun test <файл>` и `bun run typecheck`.
10. **Модули.** Если файл проходит триггер модуля (>~250 строк, ИЛИ ≥3 разнородных ответственности в одном, ИЛИ многошаговая state-машина / async-оркестрация) — оформляй его папкой: barrel `index.ts` реэкспортит только публичный API, внешние зависимости (сеть, БД) — за интерфейсом, `README.md` в папке (регистрируй в `docs/INDEX.md`, секция «Модули»), тест — co-located рядом с кодом. Потребители импортируют только barrel. Это продолжение правила №3 для сложных компонентов.
11. Для навигации по коду используй порядок: фича-док → `docs/INDEX.md` → `Grep`/`Glob` по точным сигнатурам → `Read` только нужного файла. Не читай много файлов вслепую — это экономит токены и время.
12. **Субагенты — запускать с умом.** Доступно два типа: `general-purpose` (все инструменты, умеет писать/редактировать код) и `Explore` (только чтение/поиск, без правок). Их сила — в параллельном выполнении независимой работы. Но у каждого субагента **своя чистая память (fresh context)**: он не видит текущие правки в основном окне и не знает, что делает другой параллельно запущенный агент. Поэтому:
    - **Безопасно параллелить:** разведку/поиск (Explore-агент — «найди все вызовы X», «кто использует Y»), а также запись на **изолированных, не пересекающихся по файлам** подзадачах (например, один агент пишет тесты функции A в одном файле, другой — тесты функции B в другом).
    - **Опасно параллелить:** задачи, трогающие одни и те же файлы или зависящие друг от друга. Классический пример — последовательные этапы рефакторинга (роут → сервис → компонент), где каждый следующий строится на предыдущем: параллель даст конфликты правок и «слепые» перезаписи. Такие пайплайны веди последовательно в основном окне.
    - Перед многошаговым рефакторингом запускай Explore-агента на разведку (полная карта зависимостей: кто вызывает функцию, где используются типы) — это быстрее и дешевле ручного чтения файлов, а результат встраивается в план.
13. **Коммить результат после выполненного таска, без пуша.** Когда задача завершена (код написан, `bun run typecheck` чист, тесты пройдены, форматирование применено) — делай коммит накопленных изменений локально через `git add` + `git commit`. **Не пушь** в remote — оставь пользователю проверить коммит и запушить самому. Если на текущей ветке уже есть незакоммиченные изменения от прошлых задач — коммить только то, что относится к текущей задаче (`git add <файлы>` выборочно, а не `git add -A`).

    **Единый формат сообщений — Conventional Commits:** `type(scope): описание`, описание на русском. Это даёт осмысленную историю, по которой легко читать, что и где менялось, без «угадайки» по диффу.
    - **`type`** (обязателен) — характер правки:
      - `feat` — новая функциональность (экран, компонент, эндпоинт, MCP-инструмент).
      - `fix` — исправление бага (некорректное поведение, падение, рассинхрон).
      - `refactor` — переработка кода без изменения поведения (вынос модуля, разбивка файла, переименование).
      - `perf` — улучшение производительности (memoization, устранение лишних ререндеров/запросов).
      - `style` — форматирование, порядок импортов без изменения логики.
      - `test` — добавление или правка тестов.
      - `docs` — правки документации (`AGENTS.md`, доки в `docs/`, `README`).
      - `chore` — рутина: зависимости, скрипты, не относящиеся к фиче напрямую.
      - `build` — сборка и конфигурация (`vite.config.ts`, `tsconfig.json`, `eslint.config.mjs`, docker).
      - `ci` — пайплайны CI/CD.
      - `revert` — откат предыдущего коммита.
    - **`scope`** (по возможности) — область правки: фича или слой. Берётся из контекста (`track`, `research`, `health`, `keywords`, `reviews`, `localizations`, `ai`, `mcp`, `ui`, `db`). Для сквозных правок (чаще у `chore`/`style`/`docs`) scope можно опустить — `docs: обновить AGENTS.md`.
    - **описание** — на русском, кратко и конкретно, в инфинитиве, без точки в конце: «добавить фильтр по платформе», «исправить рассинхрон рангов». Пишем про результат, а не процесс. Запрещены пустые сообщения уровня `fix`, `wip`, `правки`.

    Примеры:
    - `feat(research): добавить фильтр кандидатов по платформе`
    - `fix(track): не ронять проход трекинга при 429 от стора`
    - `refactor(health): вынести скоринг скриншотов в отдельную функцию`
    - `test(research): добавить тесты скоринга volume/difficulty`
    - `docs: обновить правило про коммиты в AGENTS.md`
    - `chore: обновить зависимости`

## Общение

14. Общайся со мной и пиши планы на русском.
15. Внутренние рассуждения (thinking/monologue) веди на английском для экономии токенов.
16. **Пиши доходчиво и человекочитаемо.** Когда объясняешь или спрашиваешь меня — раскрывай суть, а не сыпь терминами. Избегай рубленых перегруженных фраз, телеграфного стиля и плотного жаргона без расшифровки. Конкретно:
    - **Разворачивай мысль, а не клади её одной строкой.** Лучше два-три связных предложения с объяснением «почему», чем «фикс M2: single-flight» — я должен понимать, что происходит, без расшифровки терминов с твоей стороны.
    - **Термины — с расшифровкой или на plain language.** Если используешь «race condition», «barrel-файл», «code splitting» и т.п. — кратко поясни, что это значит по-человечески и зачем здесь нужно.
    - **Объясняй причину, а не только действие.** «Меняем X на Y, потому что иначе Z приводит к багу с таким-то сценарием» — лучше, чем «меняем X на Y».
    - **Когда спрашиваешь решение — давай контекст.** Не «вариант 1 или 2?», а что за выбор, какие последствия у каждого варианта, что рекомендуешь и почему.
    - **Структурируй, но не дроби до нечитаемости.** Таблицы/списки уместны для сравнения и перечислений; для объяснения концепции — связный текст, а не россыпь обрывков.
    - Применимо к: объяснениям решений, вопросам, планам, сводкам ревью. Короткие фактические ответы (статус команды, список файлов) могут быть краткими.
